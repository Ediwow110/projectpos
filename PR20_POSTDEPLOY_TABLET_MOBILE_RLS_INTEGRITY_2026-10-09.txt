2. SUPABASE SECURITY ADVISOR / RLS PERMISSIONS
===============================================
Advisor: INFO rls_enabled_no_policy, 87 affected public tables.
Guidance link:
https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy
Independent catalog/privilege verification:
- Public tables: 87.
- RLS enabled on all 87.
- RLS enabled with no policies on all 87.
- Tables granting anon SELECT: 0.
- Tables granting authenticated SELECT: 0.
- Tables readable without RLS by either role: 0.
- anon and authenticated: cannot bypass RLS.
- service_role and postgres: can bypass RLS.
INTERPRETATION: The INFO finding is compatible with the system's
server-only Postgres access model and does NOT by itself establish
a data exposure. Direct unauthenticated/authenticated Supabase API
table read access is not granted to these two roles.
IMPORTANT: Server-side DB roles can bypass RLS, so application
authentication, permissions, tenant IDs, and careful API authorization
remain essential. This review does not prove that application-layer
business logic is free of every IDOR or cross-tenant vulnerability.
Do not automatically create permissive RLS policies to silence the
advisor; that would widen the direct data access surface.
