EXTRACTION 1 — SALE REFUND SELECTION
====================================
Introduced selectSaleRefund(sale, qtyByLine, loadAmountById, threshold)
as a pure projection used by BOTH the sale-detail refund form preview and
refund API submission. It returns:
- selected merchandise refund lines
- selected gift-card-load refund amounts
- merchandise and load refund totals
- combined selected refund total
- "sale.refund" or "refund.override" permission at the strict threshold

The previous calculation was duplicated between refundAction() and the
render-time preview. Preserved:
- Number(qtyByLine[id]) positive selection and source line order
- parseMajorCurrencyToMinor() handling of load strings; parser unchanged
- Math.round((line.lineTotalMinor / line.qty) * requestedQty)
- load total sum and strict ">" approval threshold behavior
- no-sale empty selection
- server-authoritative validation, approval-token handling and error messages
- sale detail query ["sale", id], pending-payment polling and explicit refetch

No refund API contract or server-side refund policy changed.

EXTRACTION 2 — PURCHASE ORDER LINE QUANTITIES
==============================================
Added to the existing purchase-orders domain module:
- receivedPurchaseOrderQty(order, lineId)
- returnedPurchaseOrderQty(order, lineId)

The purchase-order detail page now imports these functions instead of
embedding two one-line calculations among state handlers.

Semantics maintained:
- sum every matching receipt line across receipts
- only supplier returns with status POSTED are counted
- sums are scoped to exact purchaseOrderLineId
- missing optional receipt/return arrays count as zero
- no change to barcode scan quantity, inventory receipts, return posting,
  version locking, idempotency keys or status messages.

EXTRACTION 3 — SHARED PROCUREMENT REQUEST BOUNDARY
===================================================
Added mutateProcurementRequest({online,path,init,offlineMessage,api?}).
Both purchase-order and supplier detail pages use it.

Preserved operation ordering:
1. Reject offline mutation with ApiError("NETWORK_ERROR", caller's unchanged
   offline message, "", 0).
2. GET /api/v1/auth/csrf.
3. Send original path and unchanged RequestInit with fetched csrfToken.
4. Caller performs the same detail-query refetch; purchase orders also
   perform their original events-query refetch in the original order.

No API payloads, paths, HTTP verbs, request headers, idempotency keys, or
business rules were rewritten. Certain operations (such as supplier-return
posting) retain their existing separately implemented flow; no unrequested
behavior change was made.
