# Phase 16 Design — Procurement Foundation: Suppliers & Purchase Orders

Date: 2026-10-03
Baseline: production commit `6525c38` (origin/main, Phase 15 decision point).
Branch: `codex/phase16-procurement-foundation-20261003`.

## Goal

Build the commercial procurement foundation **before** stock receiving exists:

supplier → product mapping → draft purchase order → edit → order → cancel

with tenant/branch/RBAC enforcement, idempotency, optimistic concurrency, and
audit — **without any inventory mutation**.

## Load-bearing rule (inviolable)

Creating, editing, ordering, or cancelling a purchase order MUST NOT touch
`InventoryBalance`, `InventoryMovement`, `Product` stock, `CashMovement`,
`Payment`, `Sale`, `Expense`, or `Shift`. Regression-tested at unit, contract,
pg, and e2e level. Receiving is Phase 17.

## Out of scope (Phase 17+)

Receiving (full/partial), discrepancy adjustments, supplier returns,
`PARTIALLY_RECEIVED`/`RECEIVED` states, physical counts, replenishment,
variants/bundles, landed-cost accounting, `Product.costMinor` updates from POs,
supplier payment/AP, offline PO queue.

## Domain model

### Supplier

| Field | Notes |
|---|---|
| id, businessId | app ids (`nid("sup")`), tenant FK CASCADE from Business |
| name | required, ≤120 |
| code | optional; normalized uppercase; unique per business (partial index WHERE code IS NOT NULL) |
| contactName, email, phone, addressLine1/2, city, province, postalCode | optional, bounded lengths; email format-checked by zod |
| country | default `PH` |
| paymentTerms, notes | optional, ≤80 / ≤500 |
| isActive | deactivation only; never hard-delete (history integrity) |
| createdAt, updatedAt | explicit `CURRENT_TIMESTAMP` stamping (no triggers, repo convention) |

### ProductSupplier

Relationship between existing Product and Supplier within one business.

| Field | Notes |
|---|---|
| id, businessId, productId, supplierId | product & supplier validated same-business server-side; FK RESTRICT (history-safe) |
| supplierSku | optional ≤60 |
| unitCostMinor | integer ≥ 0 (existing `*Minor` convention) |
| leadTimeDays | optional, 0–3650 |
| isPreferred | at most one preferred per product per business — partial unique index `("businessId","productId") WHERE "isPreferred"` + server clears siblings on set |
| createdAt, updatedAt | stamped |

Constraints: unique `(businessId, productId, supplierId)`. Editing this row NEVER
affects historical PO lines (lines are commercial snapshots).

### PurchaseOrder

| Field | Notes |
|---|---|
| id, businessId | `nid("po")` |
| supplierId | FK RESTRICT → Supplier |
| branchId | nullable; NULL = head-office/all-branch scope (matches existing three-mode branch design — never a fake branch). When set, must exist in business AND be active |
| poNumber | human-readable `PO-<UTC-year>-<6-digit seq>`, unique per business, generated by `POCounter` table + atomic upsert-increment inside the per-business PO advisory lock (copies `ReceiptCounter`/`nextReceiptNo` pattern exactly) |
| status | TEXT, app-enforced enum: `DRAFT` \| `ORDERED` \| `CANCELLED` (no DB enum, repo convention) |
| expectedDate, notes | optional; valid ISO date within now±(past 365d / future 365d) |
| subtotalMinor, totalMinor | server-recomputed; no procurement tax in Phase 16, so equal (fields kept for Phase 17 landed-cost compatibility) |
| version | INTEGER NOT NULL DEFAULT 1 — optimistic concurrency |
| createdBy, orderedBy, orderedAt, cancelledBy, cancelledAt, cancelReason | actor timestamps; cancel reason required (≥3 chars, expense-void precedent) |
| createdAt, updatedAt | stamped |

Indexes: unique `(businessId, poNumber)`; `(businessId, status, createdAt)`;
`(businessId, supplierId)`; `(businessId, branchId, status)`.

### PurchaseOrderLine

| Field | Notes |
|---|---|
| id, businessId, purchaseOrderId | order FK CASCADE |
| position | INTEGER, ordered like `SaleItem.position` |
| productId | same-business validated; FK RESTRICT |
| supplierSkuSnapshot | optional snapshot |
| productNameSnapshot | NOT NULL snapshot (audit convention: survives later renames) |
| quantity | int > 0, DB CHECK |
| unitCostMinor | int ≥ 0, DB CHECK; omitted → server default = ProductSupplier.unitCostMinor → Product.costMinor → 0 |
| lineTotalMinor | server-derived `quantity × unitCostMinor`, never client-trusted |
| notes | optional ≤200 |
| createdAt, updatedAt | stamped |

Constraints: unique `(businessId, purchaseOrderId, productId)` — no duplicate
product lines, DB-enforced.

### POCounter

Mirror of `ReceiptCounter`: id, businessId (unique), seq. No FK-less deviation.
All five tables get `ENABLE ROW LEVEL SECURITY` at creation (deny-all like every
table since 0017; the API owner role bypasses — no policy changes, no grants).

Migration: `0028_procurement` (next after `0027_receipt_delivery_rls`), forward
only, additive, applied at boot by `scripts/apply-migrations.mjs`.

## State machine

```
DRAFT    → ORDERED | CANCELLED
ORDERED  → CANCELLED            (allowed: Phase 16 has no receiving, cancel is
                                 the only exit from ORDERED — documented rule)
CANCELLED → terminal            (no reorder, no edits)
```

Pure transition guard in `apps/api/src/procurement/purchase-order-math.ts`
(copy of `transfer-math.ts` precedent). Illegal transitions throw
`PURCHASE_ORDER_INVALID_STATE` → 409.

Rules:
- ORDERED/CANCELLED: no line edits, no supplier/branch/cost/quantity/date/notes edits.
- Empty lines: a DRAFT may exist with zero lines; ORDERING requires ≥1 line.
- Supplier must be ACTIVE at order time (and at PO create). A DRAFT attached to a
  later-deactivated supplier stays readable/editable (may keep that supplier on
  save) but cannot be ordered: `SUPPLIER_INACTIVE` 409. New POs cannot select
  inactive suppliers; switching supplier on an existing draft requires the new
  supplier active. Deliberate rule, tested.

## Permissions (RBAC)

Existing convention: dot-keys in `SENSITIVE_ACTIONS` (@pos/auth), role→grant map
in `ROLE_SEED` (tenant/seed.ts), inline `rolePermissions(role).includes(...)`
checks, server-authoritative. Adding:

| Key | Grants |
|---|---|
| `supplier.write` | owner, manager, inventory (NOT cashier) |
| `purchase_order.write` | owner, manager, inventory |
| `purchase_order.order` | owner, manager, inventory |
| `purchase_order.cancel` | owner, manager, inventory |

`ROLE_SEED.cashier` explicitly filters all four out (its filter enumerates
exclusions — mirror that). No `*.read` keys exist in this codebase; reads stay
open to any authenticated member (like branches/products), which gives cashiers
read-only access by design. No manager-approval override is wired for
procurement (cashier writes are plain 403 `FORBIDDEN`, not approvable).
Writes without grant → 403 even for perfectly valid payloads.

## Idempotency

`Idempotency-Key` header (lowercased), missing → 400 VALIDATION; claim row in
existing `SaleIdempotency` via `findIdempotency`/`claimIdempotency`
(unique business+key+commandType; race loser → `IDEMPOTENCY_REPLAY` 200);
conflicting payload same key → `IDEMPOTENCY_MISMATCH` 409; replay returns
current state + `replayed: true`. Canonicalization: existing
`fingerprintPayload` from `sales/idempotency.ts`.

Protected commands:
- `supplier.create` (fingerprint: supplier payload)
- `purchase_order.create` (fingerprint: full draft payload incl. lines)
- `purchase_order.order` (fingerprint: {poId})
- `purchase_order.cancel` (fingerprint: {poId})

Not required (naturally replay-safe): supplier update/deactivate (idempotent by
state), PO draft update (version CAS), product-supplier create (unique pair →
409 on replay), update/remove (idempotent patches). Deliberate, documented.

## Optimistic concurrency

`version` integer on PurchaseOrder. All mutating PO endpoints require
`expectedVersion`; store does CAS (`UPDATE ... WHERE id=? AND businessId=? AND
version=?` with `version = version + 1 RETURNING`); mismatch → `STALE_VERSION`
409. Never silently overwrite. UI surfaces conflict copy + reload affordance,
refreshes its held version after each successful mutation. (Supplier/ProductSupplier
rows have no version field: single-field patches are last-write-wins by
existing catalog precedent; POs are the concurrent-edit surface the spec names.)

## Data access

Follow the transfer stack exactly:
- `DbSupplier`, `DbProductSupplier`, `DbPurchaseOrder`, `DbPurchaseOrderLine`
  interfaces + ~20 `DbPort` methods (apps/api/src/common/db.port.ts).
- Implement in `memory.db.ts` (dev/unit) AND new pg family
  `common/pg/pg-procurement.ts` wired into `PgDbPort` (Phase 12 dual-store rule).
- Tenant scoping: every method takes businessId first; `withScope()` assert;
  lookups by `(id, businessId)` → cross-tenant ids surface as `NOT_FOUND` 404.
- Locks: per-command `db.withLock("supplier:${businessId}" |
  "purchase-order:${businessId}:${id}" | "po-number:${businessId}")`;
  NO `withInventoryLocks`, no movement/balance writes anywhere.
- Audit: `db.appendAudit` with `supplier.create/update/deactivate`,
  `product_supplier.create/update/remove`, `purchase_order.create/update/
  ordered/cancelled`; `entityType` ∈ {Supplier, ProductSupplier, PurchaseOrder};
  before/after snapshots; requestId; reason for cancels. New port method
  `listAuditFor(businessId, entityType, entityId)` for the PO history section
  (bounded query — the existing global `listAudit()` stays scan-everything and
  is not used for user-facing history).
- Prisma schema.prisma: 5 models mirrored from DDL; `check-runtime-schema-parity.mjs`
  MAP gains Supplier/ProductSupplier/PurchaseOrder/PurchaseOrderLine entries.

## API surface (`/api/v1`, SessionGuard; CsrfGuard on mutations)

Suppliers:
- `GET  /suppliers?q&status=active|inactive|all&page&pageSize` (list + name search + filter)
- `POST /suppliers` (supplier.write + Idempotency-Key)
- `GET  /suppliers/:id` (detail incl. relationships count summary)
- `PATCH /suppliers/:id` (supplier.write; `isActive` only flipped via deactivate/reactivate)
- `POST /suppliers/:id/deactivate` (supplier.write) · `POST /suppliers/:id/reactivate`
- `GET  /suppliers/:id/products` · `POST /suppliers/:id/products` (supplier.write)
- `PATCH /suppliers/:id/products/:relId` · `DELETE /suppliers/:id/products/:relId` (supplier.write)

Purchase orders:
- `GET  /purchase-orders?q&supplierId&status&branchId&dateFrom&dateTo&page&pageSize`
- `POST /purchase-orders` (purchase_order.write + Idempotency-Key; lines inline)
- `GET  /purchase-orders/:id` (with lines embedded, Transfer precedent)
- `PATCH /purchase-orders/:id` (DRAFT only; supplier/branch/date/notes/lines-replace; expectedVersion)
- `POST /purchase-orders/:id/order` (purchase_order.order; Idempotency-Key; expectedVersion)
- `POST /purchase-orders/:id/cancel` (purchase_order.cancel; Idempotency-Key; reason required; expectedVersion)
- `GET  /purchase-orders/:id/events` (audit history for detail page)

Validation: zod schemas in `packages/validation/src/procurement.schema.ts`
(new, exported from index) reusing `moneyMinorSchema`/`quantitySchema`. Server
recomputes ALL totals; client totals are not a field and are ignored if sent
(strict objects). Branch: `branchId ?? auth.activeBranchId ?? null` then
validated via `findBranchById` + isActive, exactly the expense/inventory pattern.

New `CODE_STATUS` entries: `SUPPLIER_INACTIVE:409`,
`PRODUCT_SUPPLIER_DUPLICATE:409`, `PURCHASE_ORDER_INVALID_STATE:409`,
`STALE_VERSION:409`, `SUPPLIER_CODE_DUPLICATE:409`.

No billing-plan feature gate (transfers precedent).

(`suppliers` `/suppliers`, `purchaseOrders` `/purchase-orders`), shown to
owner/manager/inventory roles, NOT cashier. Discoverability e2e list extended.

Pages (Next app-router, client components, react-query `useQuery` + manual
mutations with fresh CSRF, inline `role=status`/`role=alert` feedback, no toasts
per UX-CONTRACT):
- `/suppliers` — list: search, active filter, pagination, inactive rows muted +
  "Inactive" pill; create modal; empty/loading/error states; cashier sees
  read-only (no action buttons).
- `/suppliers/[id]` — detail: contact card, edit modal, deactivate/reactivate

  filters, status pills (DRAFT=info, ORDERED=ok, CANCELLED=bad), create modal

  draft-save with Idempotency-Key.
- `/purchase-orders/[id]` — detail: header (poNumber, status pill, supplier,

Responsive: desktop/tablet/mobile per existing pages (DataTableFrame overflow,
line-editor rows stack under 768px — verify 1920/1440/1366/1280/834/768/430/390/360
via playwright projects + targeted setViewportSize loops).
A11y: labels on every input, Modal focus trap + Escape (existing component),
dialog role/name locators, status pills carry text (no color-only), disabled
buttons with `aria-disabled` semantics as existing.

require an internet connection." and disables all mutation controls; no queue,
no fake success (reads fail with existing NETWORK_ERROR inline copy).

## Deliberate business rules to document + test

1. ORDERED→CANCELLED allowed (only exit; no receiving exists).
2. Inactive supplier: readable in drafts, not selectable for new POs, ordering
   blocked with `SUPPLIER_INACTIVE`, draft save with existing inactive supplier
   allowed.
3. At most one preferred supplier per product per business (clear siblings).
4. PO lines are snapshots: later ProductSupplier cost edits never change them.
5. No tax in Phase 16 POs: subtotalMinor === totalMinor.
6. `branchId = null` means head-office scope, matching the existing three-mode
   design; no synthetic branch invented.
7. Suppliers are never hard-deleted.
